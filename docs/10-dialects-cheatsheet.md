# 10. Шпаргалка відмінностей діалектів: MySQL 8.4, MariaDB 11.4, PostgreSQL 17

## Навіщо ця тема

SQL — стандарт, але кожна СУБД має власний діалект. Код, який бездоганно працює в MySQL, може не запуститися в PostgreSQL або виконати зовсім не те, що очікувалося. Ця шпаргалка зібрана з практичних відмінностей трьох СУБД стенду: вона допомагає писати портативні запити й швидко знаходити відповідність між діалектами.

Формат кожної теми: порівняльна таблиця та приклад «одна задача — три діалекти». Навчальні дані в стенді різні: MySQL — `customers`, `products`, `orders`; MariaDB — `authors`, `books`; PostgreSQL — схема `shop` з `customers`, `products`, `orders`.

Важливо: приклади, які створюють таблиці або змінюють дані, виконуйте в **пісочниці** — база `sandbox` доступна в MySQL, MariaDB і PostgreSQL (у SQL Runner це цілі «Пісочниця …», скинути стан можна на http://localhost:8000/sandbox.php). Запити лише для читання безпечно виконувати й на навчальних базах.

Підключення:

```bash
docker exec -it learn-mysql mysql -ustudent -pstudent learn
docker exec -it learn-mariadb mariadb -ustudent -pstudent learn
docker exec -it learn-postgres psql -U student -d learn
```

У PostgreSQL перед роботою виконайте `SET search_path TO shop;`.

## 1. Ідентифікатори, регістр, рядкові літерали

| Питання | MySQL 8.4 | MariaDB 11.4 | PostgreSQL 17 |
|---|---|---|---|
| Лапки для імен | зворотні: `` `name` `` | зворотні: `` `name` `` | подвійні: `"name"` |
| Регістр імен без лапок | залежить від `lower_case_table_names` | як у MySQL | зводиться до нижнього регістру |
| Екранування апострофа | `\'` або `''` | `\'` або `''` | лише `''` (backslash не діє) |
| Подвійні лапки | рядковий літерал (без `ANSI_QUOTES`) | рядковий літерал | ідентифікатор |

```sql
-- MySQL / MariaDB
SELECT `full_name` AS "Ім'я" FROM customers;

-- PostgreSQL
SELECT "full_name" AS "Ім'я" FROM shop.customers;
```

У переносимому коді не використовуйте подвійні лапки для рядків і завжди пишіть `''` для апострофа всередині рядка.

## 2. Автоінкремент і генерація ідентифікаторів

| Дія | MySQL 8.4 | MariaDB 11.4 | PostgreSQL 17 |
|---|---|---|---|
| Оголошення | `INT AUTO_INCREMENT` | `INT AUTO_INCREMENT` | `integer GENERATED BY DEFAULT AS IDENTITY` |
| Альтернатива | — | — | `serial` / `bigserial` (застарілий стиль) |
| Початкове значення | `AUTO_INCREMENT = 1000` | `AUTO_INCREMENT = 1000` | `START WITH 1000` |
| Останній id | `LAST_INSERT_ID()` | `LAST_INSERT_ID()` | `RETURNING id`, `lastval()`, `currval()` |
| Явна вставка id | дозволена | дозволена | з `GENERATED BY DEFAULT` дозволена, з `GENERATED ALWAYS` — лише `OVERRIDING SYSTEM VALUE` |

```sql
-- MySQL / MariaDB
CREATE TABLE t_ids (
    id INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    name VARCHAR(100) NOT NULL
) ENGINE=InnoDB AUTO_INCREMENT=1000;

INSERT INTO t_ids (name) VALUES ('перший');
SELECT LAST_INSERT_ID();
```

```sql
-- PostgreSQL
CREATE TABLE t_ids (
    id integer GENERATED BY DEFAULT AS IDENTITY (START WITH 1000) PRIMARY KEY,
    name varchar(100) NOT NULL
);

INSERT INTO t_ids (name) VALUES ('перший') RETURNING id;
```

## 3. Рядкові типи та обмеження довжини

| Тип | MySQL 8.4 | MariaDB 11.4 | PostgreSQL 17 |
|---|---|---|---|
| Фіксований | `CHAR(n)`, n ≤ 255 | `CHAR(n)`, n ≤ 255 | `char(n)`, n до ~10 485 760 |
| Змінний | `VARCHAR(n)`, максимум 65 535 байтів на рядок | `VARCHAR(n)`, максимум 65 535 байтів | `varchar(n)` без практичного ліміту (до 1 ГБ) |
| Без обмеження довжини | `TEXT` (64 КБ), `MEDIUMTEXT` (16 МБ), `LONGTEXT` (4 ГБ) | `TEXT`, `MEDIUMTEXT`, `LONGTEXT` | `text` (до 1 ГБ) |
| Перевищення довжини | помилка (strict mode типово) | помилка (strict mode типово) | помилка `22001` |
| Довжина в символах | `CHAR_LENGTH(col)` | `CHAR_LENGTH(col)` | `char_length(col)` |
| Байти | `LENGTH(col)` | `LENGTH(col)` | `octet_length(col)` |

Максимальна довжина `VARCHAR` у MySQL/MariaDB обмежена не лише 65 535 байтами, а й розміром рядка InnoDB (приблизно половина сторінки 16 КБ) та кодуванням: для `utf8mb4` практична межа — близько 16 383 символів.

```sql
-- MySQL / MariaDB: перевірка довжин
SELECT CHAR_LENGTH(full_name) AS chars, LENGTH(full_name) AS bytes
FROM customers;
```

```sql
-- PostgreSQL
SELECT char_length(full_name) AS chars, octet_length(full_name) AS bytes
FROM shop.customers;
```

## 4. Дати й час

| Питання | MySQL 8.4 | MariaDB 11.4 | PostgreSQL 17 |
|---|---|---|---|
| Дата | `DATE` 1000–9999 | `DATE` 1000–9999 | `date` 4713 до н.е. — 5 874 897 |
| Дата й час без зони | `DATETIME(6)` | `DATETIME(6)` | `timestamp` |
| Дата й час із зоною | `TIMESTAMP` (UTC, діапазон до 2038) | `TIMESTAMP` (до 2038) | `timestamptz` |
| Час | `TIME`, ±838 годин | `TIME`, ±838 годин | `time`, 00:00–24:00 |
| Інтервал | типу немає, є `DATE_ADD` | типу немає, є `DATE_ADD` | `interval` |
| Поточний момент | `NOW()`, `CURRENT_TIMESTAMP` | `NOW()`, `CURRENT_TIMESTAMP` | `now()`, `CURRENT_TIMESTAMP` |
| Додати 7 днів | `DATE_ADD(now(), INTERVAL 7 DAY)` | `DATE_ADD(now(), INTERVAL 7 DAY)` | `now() + interval '7 days'` |
| Рік | `YEAR(d)`, `EXTRACT(YEAR FROM d)` | так само | `EXTRACT(YEAR FROM d)`, `date_part('year', d)` |
| Початок місяця | `DATE_FORMAT(d, '%Y-%m-01')` | так само | `date_trunc('month', d)` |
| Зона сесії | `SET time_zone = '+02:00'` | так само | `SET TIME ZONE 'Europe/Kyiv'` |

Ключова відмінність: у MySQL `TIMESTAMP` зберігається в UTC і конвертується у зону сесії, а `DATETIME` — ні. У PostgreSQL `timestamptz` зберігає момент часу, а `timestamp` — «настінний» час без зони.

```sql
-- MySQL / MariaDB
SELECT NOW() AS now_value,
       DATE_ADD(NOW(), INTERVAL 7 DAY) AS in_a_week,
       DATE_FORMAT(ordered_at, '%Y-%m-01') AS month_start
FROM orders
LIMIT 1;
```

```sql
-- PostgreSQL
SELECT now() AS now_value,
       now() + interval '7 days' AS in_a_week,
       date_trunc('month', ordered_at) AS month_start
FROM shop.orders
LIMIT 1;
```

## 5. Обмеження довжини індексів і тексту

| Питання | MySQL 8.4 | MariaDB 11.4 | PostgreSQL 17 |
|---|---|---|---|
| Максимальний ключ індексу | 3072 байти (InnoDB, DYNAMIC) | 3072 байти (InnoDB, DYNAMIC) | близько 2704 байтів для btree |
| Індекс на `TEXT` | потрібен префікс: `INDEX (body(100))` | так само | індекс на `text` можливий, але вставка завеликого значення впаде |
| Індекс на вираз | функціональний індекс: `((CAST(...)))` | немає, лише через generated column | звичайний індекс на вираз |
| Обхід ліміту | префіксний індекс | generated column + індекс | індекс на `md5(col)` або `left(col, n)` |

```sql
-- MySQL / MariaDB
CREATE INDEX idx_orders_date ON orders (ordered_at);
-- CREATE INDEX idx_products_title ON products (title(50));   -- префіксний індекс
```

```sql
-- PostgreSQL
CREATE INDEX idx_customers_email_lower ON shop.customers (lower(email));
CREATE INDEX idx_customers_email_md5 ON shop.customers (md5(email));
```

## 6. LIMIT і OFFSET

| Діалект | Синтаксис |
|---|---|
| MySQL 8.4 | `LIMIT 10 OFFSET 20` або `LIMIT 20, 10` |
| MariaDB 11.4 | `LIMIT 10 OFFSET 20`, `LIMIT 20, 10`, а також стандартний `OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY` (з 10.6) |
| PostgreSQL 17 | `LIMIT 10 OFFSET 20`, `LIMIT ALL`, `OFFSET 20 ROWS FETCH NEXT 10 ROWS ONLY` |

`LIMIT 20, 10` у PostgreSQL — синтаксична помилка: там перше число означає кількість рядків, а не зсув.

```sql
-- Одна задача: сторінка 3, по 10 рядків
-- MySQL / MariaDB
SELECT id, title FROM products ORDER BY id LIMIT 10 OFFSET 20;

-- PostgreSQL
SELECT id, title FROM shop.products ORDER BY id LIMIT 10 OFFSET 20;
```

Великі `OFFSET` дорогі в усіх трьох СУБД: сервер мусить переглянути й відкинути всі попередні рядки. Для посторінкової навігації краще «keyset pagination»:

```sql
SELECT id, title
FROM products
WHERE id > 100
ORDER BY id
LIMIT 10;
```

## 7. Конкатенація та агрегація рядків

| Дія | MySQL 8.4 | MariaDB 11.4 | PostgreSQL 17 |
|---|---|---|---|
| Конкатенація | `CONCAT(a, b)`, `CONCAT_WS()` | `CONCAT(a, b)`, `CONCAT_WS()` | `a \|\| b`, `CONCAT()` |
| Оператор `\|\|` | логічне АБО (доки не увімкнено `PIPES_AS_CONCAT`) | логічне АБО | конкатенація |
| Об'єднання значень групи | `GROUP_CONCAT(x SEPARATOR ', ')` | `GROUP_CONCAT(x SEPARATOR ', ')` | `string_agg(x, ', ')` |
| `NULL` у конкатенації | результат `NULL`; `CONCAT_WS` пропускає NULL | результат `NULL`; `CONCAT_WS` пропускає NULL | результат `NULL`; `concat()` ігнорує NULL |
| Порожній рядок | окремий від `NULL` | окремий від `NULL` | окремий від `NULL` |

```sql
-- MySQL / MariaDB
SELECT CONCAT_WS(', ', city, full_name) AS label FROM customers ORDER BY id LIMIT 3;
SELECT city, GROUP_CONCAT(full_name ORDER BY full_name SEPARATOR '; ') AS people
FROM customers
GROUP BY city;
```

```sql
-- PostgreSQL
SELECT city || ', ' || full_name AS label FROM shop.customers ORDER BY id LIMIT 3;
SELECT city, string_agg(full_name, '; ' ORDER BY full_name) AS people
FROM shop.customers
GROUP BY city;
```

## 8. Робота з NULL

| Дія | MySQL 8.4 | MariaDB 11.4 | PostgreSQL 17 |
|---|---|---|---|
| Замінити NULL | `IFNULL(x, '—')`, `COALESCE(x, '—')` | так само | `COALESCE(x, '—')` |
| Умовна логіка | `IF(умова, a, b)`, `CASE` | так само | `CASE WHEN ... THEN ... END` |
| Порівняння з NULL | `x IS NULL`, `x <=> NULL` | `x IS NULL`, `x <=> NULL` | `x IS NULL`, `x IS NOT DISTINCT FROM NULL` |
| NULL у `UNIQUE` | кілька NULL дозволено | кілька NULL дозволено | кілька NULL дозволено |
| Порядок при `ORDER BY x ASC` | NULL першими | NULL першими | NULL останніми |
| `NULLS FIRST/LAST` | не підтримується | не підтримується | підтримується |
| Агрегати (`SUM`, `AVG`) | ігнорують NULL | ігнорують NULL | ігнорують NULL |

```sql
-- MySQL / MariaDB
SELECT full_name, IFNULL(city, 'невідомо') AS city
FROM customers
ORDER BY city IS NULL, city;

SELECT id, full_name FROM customers WHERE city <=> NULL;   -- null-safe порівняння
```

```sql
-- PostgreSQL
SELECT full_name, COALESCE(city, 'невідомо') AS city
FROM shop.customers
ORDER BY city NULLS LAST;
```

## 9. Upsert: вставити або оновити

| Діалект | Інструмент |
|---|---|
| MySQL 8.4 | `INSERT ... ON DUPLICATE KEY UPDATE`, `INSERT IGNORE`, `REPLACE INTO` |
| MariaDB 11.4 | `INSERT ... ON DUPLICATE KEY UPDATE`, `REPLACE INTO` |
| PostgreSQL 17 | `INSERT ... ON CONFLICT (col) DO UPDATE`, `DO NOTHING` |

```sql
-- MySQL 8.4 (новий синтаксис зі псевдонімом рядка)
INSERT INTO products (id, title, price, stock)
VALUES (3, 'Навушники Sony WH-CH720', 3999.00, 50) AS new
ON DUPLICATE KEY UPDATE
    price = new.price,
    stock = new.stock;
```

```sql
-- MariaDB 11.4 (VALUES(col) — єдиний доступний варіант)
INSERT INTO products (id, title, price, stock)
VALUES (3, 'Навушники Sony WH-CH720', 3999.00, 50)
ON DUPLICATE KEY UPDATE
    price = VALUES(price),
    stock = VALUES(stock);
```

```sql
-- PostgreSQL 17 (пісочниця)
INSERT INTO products (id, title, price, stock)
VALUES (3, 'Навушники Sony WH-CH720', 3999.00, 50)
ON CONFLICT (id) DO UPDATE
SET price = EXCLUDED.price,
    stock = EXCLUDED.stock;

-- Або ігнорувати конфлікт:
INSERT INTO products (id, title, price, stock)
VALUES (3, 'Навушники Sony WH-CH720', 3999.00, 50)
ON CONFLICT (id) DO NOTHING;
```

Аналог `INSERT IGNORE` у PostgreSQL — `ON CONFLICT DO NOTHING`. `REPLACE INTO` діє грубо: спершу видаляє конфліктний рядок, потім вставляє новий, тому спрацьовують каскадні видалення й втрачаються значення стовпців, яких не було у вставці.

## 10. JSON

| Питання | MySQL 8.4 | MariaDB 11.4 | PostgreSQL 17 |
|---|---|---|---|
| Тип | `JSON` (бінарний, валідується) | `JSON` = `LONGTEXT` + `CHECK (JSON_VALID(...))` | `json`, `jsonb` (бінарний, індексується) |
| Витяг як JSON | `payload->'$.city'` | `JSON_QUERY(payload, '$.city')` | `payload->'city'` |
| Витяг як текст | `payload->>'$.city'` | `JSON_VALUE(payload, '$.city')` | `payload->>'city'` |
| Вкладені шляхи | `payload->>'$.address.city'` | `JSON_VALUE(payload, '$.address.city')` | `payload#>>'{address,city}'` |
| Перевірка входження | `JSON_CONTAINS(payload, '"Київ"', '$.city')` | `JSON_CONTAINS(...)` | `payload @> '{"city": "Київ"}'`, `payload ? 'city'` |
| Побудова | `JSON_OBJECT('a', 1)`, `JSON_ARRAY(1,2)` | `JSON_OBJECT`, `JSON_ARRAY` | `jsonb_build_object('a', 1)`, `jsonb_build_array(1,2)` |
| Розгортання масиву | `JSON_TABLE` | `JSON_TABLE` (10.6+) | `jsonb_array_elements(payload)` |
| Індекс | функціональний або generated column | generated column (`PERSISTENT`) + індекс | GIN: `USING gin (payload jsonb_path_ops)` |

```sql
-- MySQL 8.4
CREATE TABLE events (
    id INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    payload JSON NOT NULL
) ENGINE=InnoDB;

INSERT INTO events (payload) VALUES
    (JSON_OBJECT('city', 'Київ', 'kind', 'click')),
    (JSON_OBJECT('city', 'Львів', 'kind', 'view'));

SELECT payload->>'$.city' AS city FROM events;
SELECT * FROM events WHERE payload->>'$.city' = 'Київ';

ALTER TABLE events
    ADD COLUMN city VARCHAR(80) GENERATED ALWAYS AS (CAST(payload->>'$.city' AS CHAR(80))) STORED,
    ADD INDEX idx_events_city (city);
```

```sql
-- MariaDB 11.4
CREATE TABLE events (
    id INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    payload LONGTEXT NOT NULL CHECK (JSON_VALID(payload))
) ENGINE=InnoDB;

INSERT INTO events (payload) VALUES
    ('{"city": "Київ", "kind": "click"}'),
    ('{"city": "Львів", "kind": "view"}');

SELECT JSON_VALUE(payload, '$.city') AS city FROM events;

ALTER TABLE events
    ADD COLUMN city VARCHAR(80) AS (JSON_VALUE(payload, '$.city')) PERSISTENT,
    ADD INDEX idx_events_city (city);
```

```sql
-- PostgreSQL 17 (пісочниця)
CREATE TABLE events (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    payload jsonb NOT NULL
);

INSERT INTO events (payload) VALUES
    ('{"city": "Київ", "kind": "click"}'),
    ('{"city": "Львів", "kind": "view"}');

SELECT payload->>'city' AS city FROM events;
SELECT * FROM events WHERE payload @> '{"city": "Київ"}';

CREATE INDEX idx_events_payload ON events USING gin (payload jsonb_path_ops);
```

Порівняння `json` і `jsonb` у PostgreSQL: `json` зберігає текст як є (порядок ключів, пробіли), `jsonb` розбирає й оптимізує структуру, тому швидший для запитів та індексів.

## 11. Повнотекстовий пошук

| Питання | MySQL 8.4 | MariaDB 11.4 | PostgreSQL 17 |
|---|---|---|---|
| Об'єкт | `FULLTEXT INDEX` | `FULLTEXT INDEX` | `tsvector` + індекс GIN |
| Запит | `MATCH(...) AGAINST(...)` | `MATCH(...) AGAINST(...)` | `tsv @@ to_tsquery(...)` |
| Режими | natural language, boolean | natural language, boolean | `plainto_tsquery`, `websearch_to_tsquery`, `phraseto_tsquery` |
| Мова/стемінг | залежить від парсера | залежить від парсера | словники (`simple`, `english`, ...) |
| Мінімальна довжина слова | 3 символи (`innodb_ft_min_token_size`) | 3 символи | не обмежена |
| Стоп-слова | вбудований список | вбудований список | залежить від словника |
| Оцінка релевантності | `MATCH ... AS score` | `MATCH ... AS score` | `ts_rank()`, `ts_rank_cd()` |
| Індекс | `FULLTEXT` (InnoDB) | `FULLTEXT` (InnoDB) | `GIN` на `tsvector` |

```sql
-- MySQL / MariaDB
CREATE TABLE articles (
    id INT UNSIGNED NOT NULL AUTO_INCREMENT PRIMARY KEY,
    title VARCHAR(200) NOT NULL,
    body TEXT NOT NULL,
    FULLTEXT KEY ft_articles (title, body)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO articles (title, body) VALUES
    ('Транзакції в MySQL', 'Блокування та рівні ізоляції'),
    ('MongoDB для початківців', 'Документи та агрегаційний конвеєр');

SELECT id, title,
       MATCH(title, body) AGAINST ('блокування ізоляції' IN NATURAL LANGUAGE MODE) AS score
FROM articles
WHERE MATCH(title, body) AGAINST ('блокування ізоляції' IN NATURAL LANGUAGE MODE)
ORDER BY score DESC;

SELECT id, title
FROM articles
WHERE MATCH(title, body) AGAINST ('+транзакції -MongoDB' IN BOOLEAN MODE);
```

```sql
-- PostgreSQL (пісочниця)
CREATE TABLE articles (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title text NOT NULL,
    body text NOT NULL
);

ALTER TABLE articles
    ADD COLUMN tsv tsvector GENERATED ALWAYS AS (
        to_tsvector('simple', coalesce(title, '') || ' ' || coalesce(body, ''))
    ) STORED;

CREATE INDEX idx_articles_tsv ON articles USING gin (tsv);

INSERT INTO articles (title, body) VALUES
    ('Транзакції в PostgreSQL', 'Блокування та рівні ізоляції'),
    ('MongoDB для початківців', 'Документи та агрегаційний конвеєр');

SELECT id, title, ts_rank(tsv, query) AS rank
FROM articles, plainto_tsquery('simple', 'блокування ізоляції') AS query
WHERE tsv @@ query
ORDER BY rank DESC;

SELECT title
FROM articles
WHERE tsv @@ websearch_to_tsquery('simple', 'транзакції -MongoDB');
```

Для української мови в PostgreSQL типово використовують словник `simple`: він зводить слова до нижнього регістру, але не виконує стемінг. Тому форма слова має значення: «блокування» знайдеться, «блокувань» — ні. У MySQL/MariaDB для InnoDB діє той самий принцип, плюс мінімальна довжина токена.

## 12. Віконні функції

| Функція / можливість | MySQL 8.4 | MariaDB 11.4 | PostgreSQL 17 |
|---|---|---|---|
| `ROW_NUMBER`, `RANK`, `DENSE_RANK` | так | так | так |
| `LAG`, `LEAD`, `FIRST_VALUE`, `LAST_VALUE` | так | так | так |
| `SUM() OVER`, `AVG() OVER` | так | так | так |
| `FILTER (WHERE ...)` | ні | ні | так |
| Рамка `GROUPS` | ні | ні | так |
| Іменовані вікна `WINDOW w AS (...)` | так | так | так |

```sql
-- Однакова форма для всіх трьох діалектів (приклад для MySQL/MariaDB)
SELECT
    full_name,
    city,
    COUNT(*) OVER (PARTITION BY city) AS city_count,
    ROW_NUMBER() OVER (PARTITION BY city ORDER BY full_name) AS row_in_city
FROM customers
ORDER BY city, row_in_city;
```

```sql
-- PostgreSQL: те саме для схеми shop
SELECT
    full_name,
    city,
    COUNT(*) OVER (PARTITION BY city) AS city_count,
    ROW_NUMBER() OVER (PARTITION BY city ORDER BY full_name) AS row_in_city
FROM shop.customers
ORDER BY city, row_in_city;
```

Різниця проявляється, коли потрібне умовне агрегування: у PostgreSQL достатньо `count(*) FILTER (WHERE city = 'Київ')`, а в MySQL/MariaDB доводиться писати `SUM(CASE WHEN city = 'Київ' THEN 1 ELSE 0 END)`.

## 13. Схеми, бази та пошуковий шлях

| Поняття | MySQL 8.4 | MariaDB 11.4 | PostgreSQL 17 |
|---|---|---|---|
| База і схема | те саме; `CREATE DATABASE` = `CREATE SCHEMA` | так само | різні рівні: база містить схеми |
| Перемикання | `USE learn` | `USE learn` | `SET search_path TO shop` |
| Поточна | `SELECT DATABASE()` | `SELECT DATABASE()` | `SHOW search_path`, `current_schema()` |
| Список | `SHOW DATABASES` | `SHOW DATABASES` | `\l`, `\dn` |
| Повне ім'я | `learn.customers` | `learn.customers` | `learn.shop.customers` (база.схема.таблиця) |
| Права | на базу | на базу | на схему та об'єкти окремо |

У стенді PostgreSQL навчальні таблиці лежать у схемі `shop`, тому або вказуйте `shop.customers`, або виконуйте `SET search_path TO shop;` на початку сесії.

## 14. Послідовності

| Дія | MySQL 8.4 | MariaDB 11.4 | PostgreSQL 17 |
|---|---|---|---|
| Окрема послідовність | немає | `CREATE SEQUENCE` | `CREATE SEQUENCE` |
| Наступне значення | — | `NEXT VALUE FOR seq`, `NEXTVAL(seq)` | `nextval('seq')` |
| Поточне значення | — | `PREVIOUS VALUE FOR seq` | `currval('seq')` |
| Змінити позицію | — | `ALTER SEQUENCE ... RESTART` | `setval('seq', n)` |
| Пов'язати з колонкою | `AUTO_INCREMENT` | `AUTO_INCREMENT` | `serial`, identity, `DEFAULT nextval(...)` |

```sql
-- MariaDB
CREATE SEQUENCE seq_customer START WITH 1000 INCREMENT BY 1;
SELECT NEXT VALUE FOR seq_customer;
DROP SEQUENCE seq_customer;
```

```sql
-- PostgreSQL
CREATE SEQUENCE customer_seq START WITH 1000 INCREMENT BY 1;
SELECT nextval('customer_seq');
SELECT currval('customer_seq');
SELECT setval('customer_seq', 2000, true);
DROP SEQUENCE customer_seq;
```

У MySQL 8.4 окремих послідовностей немає: ідентифікатори генерує `AUTO_INCREMENT` у межах таблиці, а «дістати» значення можна лише через `LAST_INSERT_ID()`.

## 15. RETURNING і отримання результату запису

| Можливість | MySQL 8.4 | MariaDB 11.4 | PostgreSQL 17 |
|---|---|---|---|
| `INSERT ... RETURNING` | ні | так (10.5+) | так |
| `UPDATE ... RETURNING` | ні | ні | так |
| `DELETE ... RETURNING` | ні | так (10.0+) | так |
| Останній id | `LAST_INSERT_ID()` | `LAST_INSERT_ID()` | `RETURNING id` |
| Кількість змінених рядків | `ROW_COUNT()` | `ROW_COUNT()` | діагностика клієнта, `GET DIAGNOSTICS` у PL/pgSQL |

```sql
-- MySQL 8.4: двофазний підхід
INSERT INTO customers (full_name, email, city)
VALUES ('Новий Клієнт', 'new@example.com', 'Житомир');

SELECT LAST_INSERT_ID() AS new_id;
SELECT * FROM customers WHERE id = LAST_INSERT_ID();
```

```sql
-- MariaDB 11.4
INSERT INTO customers (full_name, email, city)
VALUES ('Новий Клієнт', 'new@example.com', 'Житомир')
RETURNING id, created_at;
```

```sql
-- PostgreSQL 17 (пісочниця)
INSERT INTO customers (full_name, email, city)
VALUES ('Новий Клієнт', 'new@example.com', 'Житомир')
RETURNING id, created_at;
```

## Типові помилки

1. **`LIMIT offset, count` у PostgreSQL.** Синтаксис не підтримується; використовуйте `LIMIT count OFFSET offset`.
2. **Рядкова конкатенація через `||` у MySQL/MariaDB.** Без режиму `PIPES_AS_CONCAT` це логічне АБО, і запит мовчки поверне не те.
3. **Очікування `RETURNING` у MySQL.** У 8.4 його немає; єдиний шлях — `LAST_INSERT_ID()` і додатковий `SELECT`.
4. **`VALUES(col)` у MySQL 8.4.** Синтаксис застарілий; використовуйте псевдонім рядка `AS new`.
5. **Однакові очікування щодо NULL-сортування.** ASC у MySQL ставить NULL першими, у PostgreSQL — останніми.
6. **Перенесення `TEXT` з індексом.** У MySQL потрібен префікс або generated column; у PostgreSQL повний індекс на `text` може впасти на великих значеннях.
7. **JSON як `jsonb` без потреби у збереженні формату.** Для пошуку краще `jsonb`; `json` варто брати, коли важливий точний текст.
8. **Повнотекстовий пошук українською зі словником `english`.** Слова не знайдуться; використовуйте `simple` (з розумінням відсутності стемінгу).
9. **`GROUP_CONCAT` без `SEPARATOR` і перенесення в PostgreSQL.** У PostgreSQL функція називається `string_agg` і порядок задається всередині виклику.
10. **Забутий `search_path` у PostgreSQL.** Таблиці `shop` не знайдуться без схеми у запиті або налаштованого шляху пошуку.
11. **`GENERATED ALWAYS AS IDENTITY` із явним id.** Вставка значення завершиться помилкою; беріть `GENERATED BY DEFAULT`, якщо id іноді задають вручну.
12. **Однакова поведінка DDL у транзакції.** У MySQL DDL викликає неявний `COMMIT`, у PostgreSQL — ні.
